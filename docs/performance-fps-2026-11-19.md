# FPS向上のための描画スレッド・GPU処理の軽量化

2026-11-18〜19。変更前: `46b94f0`。

FPSを最大の目標に、描画スレッド（クライアントのメインスレッド）とGPUの照射処理を計測し、品質を変えずに削減できる処理を削った。

## 計測で分かったこと

128灯・射程256・実照度ONの性能シーン（`-PgpuPerf`）をJFRで記録したところ、描画スレッドのJavaサンプルの42%が `GpuLightGeometry.select` → `Cache.find` → `LightReach.hidden`（壁による遮蔽判定）だった。原因は次の連鎖である。

1. バニラは受信した光データの適用時（`ClientPacketListener.readSectionList`、チャンク読み込み後の `enableChunkLight`）に `setSectionDirtyWithNeighbors` を呼ぶ。
2. CMSの `WorldEvents` はこれを周囲27区画の「区画変更」として通知する。
3. CLLはこれを形状の変更として扱い、GPU照射のメッシュ所属・照射範囲・遮蔽キャッシュを破棄していた。
4. 次のフレームで、全照明が所属区画の探索（`find`）を最初からやり直していた。

これらのキャッシュは光ではなくブロック形状だけに依存する。チャンクの形状はチャンク読み込みイベントで別に通知され、従来どおり処理される。

## 変更内容

- **光だけの区画更新を形状変更として扱わない。** 上の2メソッドの実行中に通知された区画変更を、CLLの形状キャッシュ（モデル・GPUメッシュ・照射範囲・所属区画）では無視する（`LightOnlySectionsMixin`、`LightOnlyUpdates`）。バニラでこの通知を出すのはこの2メソッドだけであることを確認した。他のmodが形状変更のために呼ぶ場合は従来どおり処理する。地形自体の再構築はバニラのまま変えていない。
- **照射円錐の外のメッシュを描かない。** 4灯ずつの表面照射で、メッシュの範囲が各灯の照射円錐（シェーダーと同じ形状、0.05ブロックの余裕付き）に入らない灯をマスクから外す。どの灯にも入らないメッシュは描画しない。灯が画面に映るかの判定にも同じ条件を使う。シェーダーは円錐外で0を返すため、結果は変わらない。
- **頂点シェーダーで使わない灯の計算を省く。** 描画中のメッシュで有効でない灯（`ActiveMask` の外）について、光源空間の座標変換を省く。フラグメントシェーダーはこれらの値を読まない。
- **空中ビームの光線判定。** 1本の光線で連続するブロックは同じチャンクにあることが多いため、チャンクの取得を通過するチャンクごとに1回にした。空気ブロックの判定を、副作用のないCMSの範囲判定より先に行う。

照度の計算式、影マップ、シェーダーの照射計算、キャッシュの上限は変更していない。

## 試して採用しなかったもの

- **動く照明の所属区画を、広げた円錐で使い回す。** 首振り中は毎フレーム探索し直しているため、5°広げた円錐で選んだ区画を再利用する案を実装した（包含関係はユニットテストで100万点以上確認）。しかし壁による遮蔽判定は光源の正確な位置でしか成り立たないため、この案では遮蔽判定を外す必要がある。外すと閉じた部屋の外の区画まで選ばれ、共有形状の上限64MiBに達してGPU照射が0灯になった。遮蔽判定を光源の移動に対応させるには `LightReach` の作り直しが必要なため採用しなかった。
- **影の描画で照射円錐の外の遮蔽物を省く。** 理屈の上では影の結果を変えないが、既存の画素比較は本番と同じ影マップを使うため、この変更を独立に検証できなかった。品質を保証できないため採用しなかった。

## 性能比較

Windows 11、Minecraft 1.21.1 / NeoForge 21.1.219 / Create 6.0.10。1280×720、VSync無効、上限260fps。変更前（`46b94f0`）と変更後を別のチェックアウトで交互に実行した。この環境は同じ条件でも実行ごとに±10〜15%程度ばらつくため、複数回の値を記載する。

**チャンク読み込み・実照度の同期中（view=0）**。光データの受信が続く区間で、今回の主な改善が効く。

| シーン | 指標 | 変更前 | 変更後 |
|---|---|---:|---:|
| 128灯・静止（2回） | フレーム時間中央値 | 8.912 / 8.971ms | 7.933 / 7.935ms（−11%） |
| 128灯・静止（2回） | 区間内の描画フレーム数 | 1064 / 1065 | 1164 / 1141（+9%） |
| 64灯・首振り | フレーム時間中央値 | 13.759ms | 13.702ms |
| 64灯・首振り | 最大フレーム時間 | 194.25ms | 31.39ms |

同じ50秒間のJFR記録（128灯）で、描画スレッドのJavaサンプルは476 → 108（−77%）。このうち `find` は192 → 0。

**静止した視点（view=1・2）**。読み込みが終わった後の定常状態。

| シーン | 視点 | 変更前 | 変更後 |
|---|---|---:|---:|
| 128灯・静止（2回） | view=1 | 6.184 / 5.559ms | 5.775 / 5.747ms |
| 128灯・静止（2回） | view=2 | 9.315 / 6.638ms | 6.700 / 7.068ms |
| 64灯・首振り | view=1 | 11.243ms | 11.232ms |
| 64灯・首振り | view=2 | 12.425ms | 12.251ms |

定常状態の差はばらつきの範囲内。128灯のシーンはGPU律速で、照射処理のGPU時間（約4.3ms）がフレームの大半を占める。全灯が同じ部屋全体を照らすため、円錐による省略がほとんど効かない。照明が別々の場所を照らす実際のワールドでは描画数が減る。首振りの値は最終コードでの1回分（途中の版には採用しなかった影の省略が入っていたため除外）。
