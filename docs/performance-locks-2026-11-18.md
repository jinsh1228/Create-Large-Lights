# 照度問い合わせ・ブロック変更の軽量化

2026-11-18。変更前: `8879a76`。

描画品質・照度の値・同期内容は変えず、毎回の照度問い合わせとブロック変更で発生していたロック・走査・割り当てを削減した。

## 変更内容

- **クライアントの照度問い合わせ。** チャンクメッシュ作成スレッド・描画スレッドからのブロック光の問い合わせ（`LightFieldNetwork.values`）が、毎回ひとつの全体ロックを取っていた。有効チャンクと受信済み区画の読み取り専用ビューを公開し、照明のないチャンク・受信済み区画はロックなしで返す。未受信区画の要求登録だけロックを取る。ビューは有効・無効の切り替え時に作り直し、受信した区画はそのチャンクの配列へ書き込む。
- **サーバーの照度問い合わせ。** `LightField.sample` がワールドごとの状態を引くたびに全体ロックと `WeakHashMap` を使っていた。ワールド→状態の対応をロックなしで読めるようにし（`LevelMap`、弱参照のまま）、どの照明の索引にもないチャンクはロック・LRUキャッシュに触れず0を返す。チャンク一覧は照明の形状が変わった後の最初の問い合わせで1回だけ作り直す。
- **ブロック変更時の過去の光線の破棄。** 照明があるワールドでは、どこで `setBlock` が起きても全キャッシュ区画の全遮蔽マスク（最大8,192）を走査していた。全マスクの光線（光源から区画まで）を包む範囲を保持し、その外の変更では走査を省く。範囲はマスク作成時に広げ、全走査のたびに残ったマスクへ縮める。破棄されるマスクと結果は従来と同一。
- **`LightReach`。** `hidden`・`bounds` が同じキャッシュを2〜3回引いていたのを1回にした。
- **投光器本体の描画。** 1灯1フレームごとに作っていた行列2個・法線配列・ベクトルを、既存の頂点用と同じ描画スレッド専用の作業領域にした。CMSへ渡す行列と、光線・GPU投影が保持するベクトルは従来どおり毎回作る。
- **配布JAR内のJSON。** ビルド時に、文字列の外の空白だけを除く（モデル・言語・レシピ等26ファイル、53,227 → 24,799 bytes）。ソースは整形したまま。全ファイルで解析結果がソースと一致することを確認した。

照度の計算式、遮蔽判定、キャッシュの上限、同期の予算、GPU描画とシェーダーは変更していない。

## 性能比較

Windows 11、Temurin 21.0.11。ユニットテスト環境で `LightField.Field` を直接計測（64灯・射程128、遮蔽マスク2,594個、321区画）。変更前は同じテストを `8879a76` に入れて計測。5回の最良値。両者の照度の合計値は一致（12,601,600）。

| 処理 | 変更前 | 変更後 |
|---|---:|---:|
| 照明のないチャンクの照度問い合わせ | 105.7 ns | 4.8 ns |
| 同上、4スレッド同時（1回あたりの経過時間） | 202.9 ns | 2.3 ns |
| 照らされたセルの照度問い合わせ（キャッシュ済み） | 79.9 ns | 59.8 ns |
| 光線から離れた場所のブロック変更 | 36,769 ns | 69 ns |

ブロック変更の値はマスク数に比例するため、上限の8,192個では変更前は約3倍になる。Createの構造物の組み立て・解体など、1tickに多数のブロックが変わる場面で効く。

クライアントの照度問い合わせはMinecraftのワールドが必要なためユニットテストでは計測していない。変更前はチャンクメッシュ作成の全スレッドと描画スレッドが同じロックを取り合っていた。FPSの実測比較は行っていない。
